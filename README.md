## 2. Предметна область

Це клієнт-серверна система для керування розумними пристроями: backend-сервіс на Spring Boot (REST + WebSocket) зберігає пристрої, команди та права доступу, а користувачі працюють через консольний застосунок із текстовим меню, який звертається до цього API — обираєш пункт за номером (додати пристрій, обрати команду, ввести аргументи тощо). Кожен пристрій представлений окремим GUI-симулятором на тому самому стеку: він отримує токен, підключається по WebSocket і тримає власний стан, напр. `{"isOn": true, "brightness": 70}` для лампи/ Команди від користувача сервіс пересилає саме йому на виконання.

У межах цієї системи можна віддалено керувати підключеними пристроями, обмежувати доступ користувачів до пристроїв або окремих команд, надавати й відкликати цей доступ іншим людям, а також перевіряти логи виконання команд. Доступ розмежовується за ролями по кожному пристрою окремо: власник може дозволити заборонити доступ до певних команд користувачам, з рівнем "Гість". 

## 3. Ролі та права доступу

### Власник може:
* додавати нові команди на пристрої;
* надавати й відкликати доступ інших користувачів;
* виконувати будь-яку команду на пристрої;
* переглядати повний журнал пристрою;
* прибрати пристрій зі свого акаунту;
* видалити пристрій повністю, для всіх користувачів.

### Гість може лише:
* виконувати команди, які "Власник" позначив доступними "Гостям";
* переглядати в журналі лише власні записи;
* прибрати пристрій зі свого акаунту.

## 4. Цільові пристрої

| Пристрій | Команди | Тип команди |
|---|---|---|
| Лампа | `turn_on`, `turn_off`, `set_brightness` | перемикач + числовий параметр |
| Чайник | `turn_on`, `turn_off` | перемикач + цільове значення |
| Кондиціонер | `set_temperature`, `set_mode` | цільове значення + вибір режиму |
| Кавомашина | `turn_on`, `turn_off` | перемикач + довготривала команда (виконується не миттєво) |
| Розумні жалюзі | `open`, `close`, `set_position` | керування позицією 0–100 |

## 5. Бізнес-кейси

1. **Додавання пристрою**
   - Користувач запускає симулятор пристрою (наприклад "лампа"), і той видає одноразовий токен підключення.
   - Користувач вводить цей токен у клієнті — пристрій додається до його акаунту, і він одразу стає його власником.

2. **Додавання нової команди** *(лише Власник)*
   - Власник обирає пристрій і додає нову команду: вказує назву, потрібні аргументи та чи буде вона доступна гостям.
   - Команда одразу стає доступною для виконання тим, кому дозволено за роллю.

3. **Надання доступу іншому користувачу** *(лише Власник)*
   - Власник обирає пристрій, вказує людину (за email) і призначає їй роль — "Власник" або "Гість".
   - Пристрій одразу з'являється в списку пристроїв запрошеного користувача з цією роллю.

4. **Виконання команди**
   - Користувач обирає пристрій і команду, доступну його ролі на цьому пристрої, вводить потрібні аргументи та запускає виконання.
   - Пристрій виконує дію та повертає результат. 
   - Виклику і результат зберігаються в базі даних на сервері.

5. **Відкликання доступу** *(лише Власник)*
   - Власник прибирає користувача зі списку тих, хто має доступ до пристрою.
   - Пристрій одразу зникає зі списку "мої пристрої" цього користувача.

6. **Видалення пристрою**
   - Гість може прибрати пристрій лише зі свого акаунту — в інших користувачів він лишається без змін.
   - Власник додатково може видалити пристрій повністю, для всіх користувачів.
   - Перед остаточним видаленням користувач підтверджує свій вибір.

7. **Перевірка логів**
   - Користувач відкриває журнал пристрою: Власник бачить усі виконані команди, Гість — лише свої.

## 6. Схема процесу

Наскрізний потік від підключення пристрою до перевірки логів, що поєднує всі кейси вище в одну картину:

```
Реєстрація / вхід в акаунт (email)
   → Запуск симулятора пристрою, отримання одноразового токена
   → Введення токена в клієнті — пристрій додано, роль = Власник
   → Власник додає нову команду для пристрою (назва, аргументи, доступність Гостям)
   → (опційно) Надання доступу іншому користувачу з роллю Власник/Гість
   → Вибір пристрою і команди, введення аргументів
   → Сервіс перевіряє роль користувача на сервері
   → Виконання команди на пристрої
   → Результат записується в журнал пристрою
   → Користувач бачить результат
   → Перегляд журналу (Власник — усі записи, Гість — лише свої)   
```


## 7. Модель даних

Замість вкладених списків користувачів усередині `Device` виділяємо звʼязок в окрему сутність `DeviceAccess` — нормалізовану структуру, яку зручно і зберігати в PostgreSQL, і перевіряти у Spring Security. Аналогічно, виконання команди — це не рядок у списку логів, а повноцінна сутність `CommandExecution`: WebSocket-обмін з пристроєм асинхронний, тож потрібен статус `PENDING`, поки очікуємо відповідь.

### User
| Поле | Тип | Примітка |
|---|---|---|
| `id` | `UUID` | |
| `email` | `string` | унікальний, використовується для логіну |
| `name` | `string` | |
| `passwordHash` | `string` | зберігається як хеш, ніколи в чистому вигляді |
| `createdAt` | `timestamp` | |

### Device
| Поле | Тип | Примітка |
|---|---|---|
| `id` | `UUID` | |
| `name` | `string` | задає власник при підключенні |
| `type` | `enum{LAMP, KETTLE, AC, COFFEE_MACHINE, BLINDS}` | визначає стандартний набір команд і структуру `state` |
| `connectionToken` | `string` | одноразовий, стає невалідним після використання |
| `state` | `JSON` | поточний стан симуляції, структура залежить від `type` (напр. `{"isOn": true, "brightness": 70}`) |
| `createdAt` | `timestamp` | |

### DeviceAccess
Звʼязок "хто має доступ до якого пристрою і з якою роллю".

| Поле | Тип | Примітка |
|---|---|---|
| `deviceId` | `FK → Device` | Унікальний ключ: `(deviceId, userId)`. |
| `userId` | `FK → User` | Унікальний ключ: `(deviceId, userId)`. |
| `role` | `enum{OWNER, GUEST}` | |
| `grantedById` | `FK → User` | хто надав доступ — потрібно для аудиту (кейс 3) |
| `grantedAt` | `timestamp` | |

### Command
| Поле | Тип | Примітка |
|---|---|---|
| `id` | `UUID` | |
| `deviceId` | `FK → Device` | |
| `name` | `string` | напр. `set_brightness` |
| `argsSchema` | `JSON` | опис очікуваних аргументів і типів, напр. `{"brightness": "int:0-100"}` |
| `requiredRole` | `enum{OWNER, GUEST}` | `GUEST` — доступно всім з доступом, `OWNER` — лише власникам |
| `createdAt` | `timestamp` | |

### CommandExecution
Журнал виконання — саме те, що показується в кейсі 7.

| Поле | Тип | Примітка |
|---|---|---|
| `id` | `UUID` | |
| `commandId` | `FK → Command` | |
| `deviceId` | `FK → Device` | дублюється для швидшого пошуку логів по пристрою без join |
| `executedById` | `FK → User` | |
| `args` | `JSON` | фактичні значення аргументів цього виклику |
| `status` | `enum{PENDING, RUNNING, SUCCESS, FAILED, TIMEOUT}` | `PENDING` — у черзі; `RUNNING` — передано на виконання, очікуємо відповідь; `TIMEOUT` — пристрій не відповів вчасно |
| `result` | `JSON` | що повернув пристрій |
| `requestedAt` | `timestamp` | |
| `completedAt` | `timestamp` | `null`, поки `status` у `PENDING` або `RUNNING` |

### Модель переходів `CommandExecution.status`

| Із стану | Дозволені переходи |
|---|---|
| `PENDING` | `RUNNING` |
| `RUNNING` | `SUCCESS`, `FAILED`, `TIMEOUT` |
| `SUCCESS` | — (термінальний) |
| `FAILED` | — (термінальний) |
| `TIMEOUT` | — (термінальний) |

Будь-яка спроба іншого переходу (напр. `PENDING → SUCCESS` в обхід `RUNNING`, чи вихід з термінального стану) кидає `InvalidStateTransitionException`.

## 9. REST API

### Команди
| Метод | Шлях | Тіло | Відповідь |
|---|---|---|---|
| `POST` | `/devices/{deviceId}/commands` | `{"name", "argsSchema", "requiredRole"}` | `201` + команда, заголовок `Location` |
| `GET` | `/devices/{deviceId}/commands?requiredRole=` | — | `200` + список, відсортований за `name`; `requiredRole` необов'язковий |
| `PUT` | `/devices/{deviceId}/commands/{commandId}` | `{"argsSchema", "requiredRole"}` | `204` |
| `DELETE` | `/devices/{deviceId}/commands/{commandId}` | — | `204` |

| Код | Коли |
|---|---|
| `400` | невалідне тіло або `requiredRole` не `OWNER`/`GUEST` |
| `404` | пристрій не існує, або команда не належить цьому пристрою |
| `409` | пристрій вже має команду з такою `name` |
